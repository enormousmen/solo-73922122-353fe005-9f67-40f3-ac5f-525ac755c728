# 供应商主体审校台 + 采购核销台

用于归集两套采购系统中的供应商记录：审核企业名称相同的记录对，给出“同一企业 / 不同企业”判定，最终形成入仓时使用的统一主体分组；并在分组基础上关联 ERP 采购订单与发票，按方案核销、分析尚未开票的采购金额。

- 后端：FastAPI + SQLite（WAL、`BEGIN IMMEDIATE` 事务、`busy_timeout`）
- 前端：两个单页网页（审校首页、采购核销页），无外部依赖
- 运行形态：Docker Compose 启动 **两个独立 Web 进程**（`app1`、`app2`），nginx 作为浏览器入口轮询转发，两个进程共享同一个 SQLite 数据卷
- 浏览器入口：**http://localhost:8080**（审校首页）、**http://localhost:8080/writeoffs**（采购核销页）

## 快速启动

前置条件：Docker 与 Docker Compose v2。

```bash
docker compose up --build
```

等待两个应用健康检查通过后打开：

**http://localhost:8080**

首次启动会导入两批只读种子数据（之后重启不会重新导入，也不会覆盖已有判定、分组与核销）：

- `data/suppliers.csv`：最多 100 条 `来源 / 源编号 / 企业名称` 供应商记录（本仓库附带 62 条，两套采购系统各 31 条）；
- `data/erp_documents.json`：订单、发票各最多 20 张，每张含 `单据 ID / 供应商原始记录 ID / 正整数分金额`（本仓库附带 20+20 张，供应商记录 ID 对应 CSV 前 20 条记录）。

停止：

```bash
docker compose down
```

如需清空全部数据、从种子文件重新演示（**会删除数据卷中的全部判定、分组与核销**）：

```bash
docker compose down -v
docker compose up --build
```

## 演示路径

### 1. 合并同名企业（审校首页）

1. 页面默认展示 62 条原始记录、62 个单条分组。
2. 在“同名企业候选对”中找到“华信精密制造有限公司”（A-001 / B-001），点击“同一企业”。
3. 页面先弹出预览：受影响记录的变更前/变更后分组、判定依据、变更摘要。
4. 点击“确认保存判定与分组”。返回后分组变为 61 个，“已归并分组”增加 1。
5. 用“判定工作台”再选另一条已归并记录与第三条记录判定“同一企业”，可看到同一关系传递成组（三条记录进入同一分组）。

### 2. 不同企业约束与冲突拦截

1. 对同一分组内的两条记录选择“不同企业”，预览会显示拦截原因和“同一企业”传递路径，不提供确认按钮。
2. 对两个不同分组选择“不同企业”可正常保存；此后任何会把这二者合并的“同一企业”判定都会在预览时被拒绝。

### 3. 撤回只移除一条判定

在“判定依据”或分组卡片中点击某条判定的“撤回”：

1. 先预览“撤回后分组”，例如一个分组拆成两个分组。
2. 确认后只删除该一条判定，其余同一企业关系继续生效，分组自动重算。

### 4. 采购核销（核销页）

从首页顶部导航进入“采购核销”，或直接打开 http://localhost:8080/writeoffs 。

1. **同组约束**：未合并分组前，用订单 `PO-2026-001`（供应商 A-001）核销发票 `INV-2026-001`（供应商 B-001）会被拒绝（409 `suppliers_not_in_same_group`）；先在审校首页把“华信精密制造有限公司”两条记录判定为同一企业。
2. **编辑方案**：在“核销方案编辑”中输入方案 ID（如 `方案A`），添加明细行（订单 × 发票 × 正整数分金额），保存即按方案 ID **整批替换**；“清空该方案”整批删除其明细。保存后顶部统计即时更新：已核销金额、**未开票采购金额**（订单余额合计）。
3. **跨方案分摊与累计上限**：同一张单据可出现在多个方案中。例如 `PO-2026-001` 金额 ¥12,800.00，`方案A` 核销 ¥6,400.00 后，`方案B` 最多再核销 ¥6,400.00；超出即 409 `amount_exceeded` 并指出其他方案已占用与本方案可申请余额。整批替换按“先释放本方案旧明细”后的整体结果校验，因此本方案重存相同金额不会被自己占用。
4. **按单查看明细、余额**：在“单据与余额”中点击任一订单/发票的“明细”，弹窗显示该单据总额、各方案累计核销、余额及逐条明细（方案、对方单据、金额）。
5. **拆分保护**：回到审校首页，对“华信”那条“同一企业”判定点击“撤回”——只要还有核销跨在该合并上，预览直接拒绝并列出涉及方案与明细；解除（清空）该方案核销后才能撤回拆分。若在预览之后、确认之前新增了核销，确认时同样会重新检查并拒绝（409 `writeoff_crosses_groups`），预览保持有效，解除核销后可直接再次确认。

### 5. 两个 Web 进程

页面右上角的“服务进程”显示本次响应来自 `app1` 还是 `app2`。多次刷新，nginx 会在两个进程之间轮询；无论请求落到哪个进程，看到的分组、判定、核销与余额都一致，因为全部读写都经过共享 SQLite 的串行化事务。

```bash
docker compose logs -f app1 app2

for i in 1 2 3 4; do
  curl -s -D - -o /dev/null http://localhost:8080/health | grep -i x-app-instance
done
```

### 6. 确认时的重新校验（两个标签页演示）

打开两个浏览器标签页，均指向 http://localhost:8080。

**相关改动 → 拒绝并要求重新预览：**

1. 标签页 1：对 A-001 与 B-001 点“同一企业”，停留在预览弹窗，不确认。
2. 标签页 2：对 B-001 与另一条记录（例如 A-002）判定“同一企业”并确认。
3. 回到标签页 1 点击确认：系统会重新读取所涉原组成员（A-001、B-001 及其原分组）和这些成员关联的判定，发现 B-001 的关联判定已变化，返回“预览已失效”，判定与分组均未改变。
4. 点击弹窗中的“重新预览”，确认新的前后分组后再保存。

**无关分组改动 → 不影响确认：**

1. 标签页 1：对 A-001 / B-001 预览“同一企业”，不确认。
2. 标签页 2：对完全无关的“恒达电子科技有限公司”两条记录判定“同一企业”并确认。
3. 标签页 1 直接确认仍会成功；预览只锁定所涉分组及关联判定，无关分组的变化不会阻塞。

**预览后新增核销 → 确认被拦截：**

1. 标签页 1：对已合并的“华信”判定预览“撤回”，不确认。
2. 标签页 2：在核销页保存一条跨 A-001/B-001 的核销。
3. 标签页 1 确认：返回 409 `writeoff_crosses_groups` 并指出方案；解除该核销后同一预览可直接确认。

## 数据与配置

### CSV

默认文件：`data/suppliers.csv`

支持中英文表头别名：

| 含义 | 可识别表头 |
| --- | --- |
| 来源 | `来源`, `source`, `系统`, `采购系统` |
| 源编号 | `源编号`, `source_code`, `code`, `编号` |
| 企业名称 | `企业名称`, `name`, `企业名`, `供应商名称` |

首次导入按行顺序取前 `SEED_LIMIT` 条（默认 100）。要使用自己的 CSV，可在首次启动前替换该文件，或通过环境变量指定挂载路径：

```yaml
environment:
  SEED_CSV: /app/data/my_suppliers.csv
  SEED_LIMIT: "100"
```

### 订单 / 发票 JSON

默认文件：`data/erp_documents.json`，结构如下：

```json
{
  "orders": [
    {"order_id": "PO-2026-001", "record_id": 1, "amount_cents": 1280000}
  ],
  "invoices": [
    {"invoice_id": "INV-2026-001", "record_id": 2, "amount_cents": 640000}
  ]
}
```

- `record_id` 必须引用已导入的供应商记录 ID（附带的 JSON 对应附带 CSV 的前 20 条记录；若替换 CSV，请同步调整 JSON，否则首次启动会因外键校验失败而拒绝启动）。
- `amount_cents` 必须是正整数（单位：分）。
- 首次启动各取前 `SEED_DOCS_LIMIT` 张（默认 20），重复 ID、非正金额、缺失字段都会在启动时报错。
- 载入后订单与发票只读：API 不提供修改入口，数据库触发器直接拒绝 UPDATE/DELETE。

### 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DB_PATH` | `./data/review.db` | SQLite 数据库路径；Compose 中为 `/data/review.db` |
| `SEED_CSV` | `./data/suppliers.csv` | 首次导入的供应商 CSV |
| `SEED_LIMIT` | `100` | 首次导入的最大供应商记录数 |
| `SEED_DOCS` | `./data/erp_documents.json` | 首次导入的订单/发票 JSON；文件不存在则跳过单据导入 |
| `SEED_DOCS_LIMIT` | `20` | 订单、发票各自的最大导入张数 |
| `APP_INSTANCE` | 主机名 | 页面展示的 Web 进程标识 |

## 行为与一致性规则

1. **原始记录与单据不可变**：API 不提供修改/删除记录或单据的入口；数据库 `BEFORE UPDATE/DELETE` 触发器直接拒绝。CSV 与 JSON 只在对应表为空时导入。
2. **判定唯一**：规范化记录对 `(min_id, max_id)` 上最多一条判定。重复添加相同判定会被拦截；对已有相反判定的记录对重新判定也会被拦截。
3. **同一企业传递成组**：分组是“同一企业”边的连通分量。
4. **不同企业是硬约束**：任一“不同企业”判定连接的两个分组不得合并；端点已经在同组时添加“不同企业”判定会被拒绝。
5. **核销同组约束**：每条核销明细的订单供应商与发票供应商必须属于**当前同一分组**，保存时在写事务内按当前分组校验。
6. **核销累计约束**：同一张订单/发票可跨方案分摊核销，但全部方案累计不得超过单据金额。按方案 ID 整批替换时，先释放该方案旧明细，再对释放后的整体结果校验；校验或写入任一步失败，整个替换回滚，原方案不变。清空（空明细提交）同样原子。
7. **关系变更的拆分保护**：关系变更的**预览与确认**都会用“拟分组”（变更后的分组）检查全部已保存核销；只要有一条核销的双方供应商会因此落入不同分组，即拒绝并指出涉及方案与明细（预览返回 `confirmable=false`，确认返回 409 `writeoff_crosses_groups`）。解除相关核销后方可拆分。
8. **预览**：服务端计算并保存一份快照，包含所涉原组成员 `involved_ids`、这些成员的当前分组及完整组员、任一端点属于所涉成员的全部生效判定。页面展示受影响记录的变更前/变更后分组、组员和判定依据。
9. **确认**：在 `BEGIN IMMEDIATE` 写事务中重新读取当前数据，重建同样的快照并与预览快照逐字段比较：
    - 不一致（相关成员或关联判定发生变化）→ 409，预览标记为 `stale`，**不写入任何判定/分组**，要求重新预览；
    - 一致 → 重新计算拟分组并复查核销跨组（第 7 条），通过后在同一事务内写入/删除判定、重算并覆盖保存 `groups` 与 `group_members`，再将该预览标记为 `confirmed`。
    与所涉分组无关的判定/分组变化不在快照内，因此不会影响确认。
10. **失败保留原状态**：判定、分组与核销明细的写入都在各自单事务内提交；任何校验失败或异常都回滚，原状态保持不变。
11. **重启保留**：判定、预览、分组、方案与核销明细均在 SQLite 中；启动时若记录/单据已存在则不重新导入，并依据判定重算、规范化分组表。
12. **并发等价串行**：两个进程各自按请求打开 SQLite 连接；WAL 允许多读单写，`BEGIN IMMEDIATE` + `busy_timeout` 串行化所有写事务（核销保存、关系确认）。核销保存与关系确认互斥执行，确认时读取到的核销状态必为某个已提交的完整批次；`GET /api/state` 与 `GET /api/writeoffs/state` 各自在单个读事务内取数，一次查询返回一致的分组、核销明细及余额。同一个预览被并发确认时只有一次成功，另一次得到“预览不可再次确认”。

## API 摘要

同一组 API 会被 nginx 分发到两个进程，任意进程都能处理任意请求。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/state` | 审校首页状态：记录、分组、判定依据、同名候选对、统计 |
| `POST` | `/api/previews` | 创建预览：`{"operation":"add","record_a":1,"record_b":2,"relation":"same"}` 或 `{"operation":"withdraw","decision_id":3}` |
| `POST` | `/api/previews/{id}/confirm` | 确认；body `{"snapshot_digest":"..."}` 可选，用于校验页面持有的是同一预览 |
| `POST` | `/api/previews/{id}/cancel` | 取消尚未确认的预览 |
| `GET` | `/api/writeoffs/state` | 核销页一致性快照：分组、订单/发票及余额、全部方案与核销明细、未开票统计 |
| `PUT` | `/api/schemes/{scheme_id}/writeoffs` | 按方案 ID 整批替换核销明细：`{"entries":[{"order_id":"PO-2026-001","invoice_id":"INV-2026-001","amount_cents":640000}]}`；`entries` 为空数组即清空该方案 |
| `GET` | `/health` | 健康检查，返回进程实例 |
| `GET` | `/api/meta` | 初始化信息与预览状态统计 |

冲突与拒绝：

- 关系冲突预览返回 HTTP 200，`preview.confirmable=false` 并附带 `conflict.code/message/evidence`；核销跨组冲突另附 `conflict.schemes` 与 `conflict.writeoffs`。
- 过期确认返回 HTTP 409（`preview_stale` / `preview_not_pending`）；确认时被核销拦截返回 409 `writeoff_crosses_groups`（附 `schemes`、`writeoffs`，预览保持 pending）。
- 核销保存校验失败：400 `unknown_order` / `unknown_invoice` / `invalid_amount` / `duplicate_entry` / `too_many_entries`，409 `suppliers_not_in_same_group` / `amount_exceeded`；失败均不改状态。

python3 -m venv .venv
. .venv/bin/activate

pytest -q
